TASK 3: LINUX INCIDENT SURFACE - AN OVERVIEW
============================================

Linux Attack Surface:
Potential entry points an attacker may exploit.
Examples:
- Open ports
- Running services
- Vulnerable applications
- Network communication

Linux Incident Surface:
Places where an investigator may find evidence after an incident.
Examples:
- System logs and authentication logs
- Network traffic
- Running processes
- Running services
- File and process integrity

ACTIVITY 2: INVESTIGATE NETCOM NETWORK COMMUNICATION
----------------------------------------------------

STEP 1: Start netcom
--------------------
In a terminal:
sudo su
cd /home/activities/processes
./netcom

Keep netcom running. Open another terminal.

STEP 2: Find the netcom PID
---------------------------
Command:
ps aux | grep '[n]etcom'

Actual output observed in this lab:
root  1934  ... ./netcom

PID observed: 1934

Note:
The PID can change after restarting netcom. Find it again before querying.

STEP 3: List network connections
--------------------------------
Command:
sudo lsof -i -P -n

Explanation:
lsof -> Lists open files, including network sockets.
-i   -> Selects network files/connections.
-P   -> Shows numeric port numbers.
-n   -> Shows numeric IP addresses; does not resolve hostnames.

STEP 4: Narrow lsof to the netcom process
-----------------------------------------
Command:
sudo lsof -nP -a -p 1934 -i

Explanation:
-a      -> ANDs the selected conditions.
-p 1934 -> Selects PID 1934.
-i      -> Shows network connections for that process.

STEP 5: Start osquery as root
-----------------------------
Command:
sudo osqueryi

Important:
Run osqueryi as root. The netcom process was running as root.

STEP 6: Query the process socket table
--------------------------------------
SQL:
SELECT pid, fd, socket, local_address, remote_address, remote_port
FROM process_open_sockets
WHERE pid = 1934;

Explanation:
pid            -> Process ID.
fd             -> File descriptor used by the process.
socket         -> Socket identifier.
local_address  -> Local endpoint IP address.
remote_address -> Remote endpoint IP address.
remote_port    -> Remote destination port.

Actual output previously observed for the columns without remote_port:
PID:            1934
Local address:  10.49.154.40
Remote address: 68.53.23.246

Room answer for remote IP:
68.53.23.246

Room answer for remote port:
443

Note:
The user's pasted query did not include remote_port, so 443 was not shown
in that pasted output. The room answer is 443. To display it on the VM,
run the full SQL query above while netcom is still running.

To exit osquery:
Press Ctrl+D.

Persistence means maintaining access to a system after initial access.
This room demonstrates account, cron and service persistence.

ACTIVITY 1: ACCOUNT CREATION DEMONSTRATION
------------------------------------------

STEP 1: Create the lab account

ACTIVITY 2: CRON JOB PERSISTENCE
--------------------------------

Cron is a time-based scheduler. A cron entry can run a command at a
specified time or at reboot.

STEP 1: List the current user's cron entries
--------------------------------------------
Command:
crontab -l

STEP 2: Open the crontab editor (only if following the lab demonstration)
--------------------------------------------------------------------------
Command:
crontab -e

Example entry shown in the room:
@reboot /path/to/malicious/script.sh

Explanation:
@reboot -> Runs the specified command when the system boots.

Note:
/path/to/malicious/script.sh is a placeholder in the room example. Do not
add a non-existent or unwanted script as a real cron entry.

STEP 3: Inspect per-user cron files
-----------------------------------
Command:
sudo ls -la /var/spool/cron/crontabs/


ACTIVITY 3: SYSTEMD SERVICE PERSISTENCE DEMONSTRATION
-----------------------------------------------------

The room demonstrates creating a service named suspicious.service.
This is separate from the pre-existing benign.service used in the
room's service-investigation questions.

STEP 1: Create the demonstration service file
---------------------------------------------
Command:
sudo tee /etc/systemd/system/suspicious.service > /dev/null <<'UNITFILE'
[Unit]
Description=Suspicious_Service
After=network.target

[Service]
ExecStart=/home/activities/processes/suspicious
Restart=on-failure
User=nobody
Group=nogroup

[Install]
WantedBy=multi-user.target
UNITFILE

STEP 2: Reload systemd configuration
------------------------------------
Command:
sudo systemctl daemon-reload

STEP 3: Enable the service at startup
------------------------------------
Command:
sudo systemctl enable suspicious.service

STEP 4: Start the service
-------------------------
Command:
sudo systemctl start suspicious.service

STEP 5: Check service status
----------------------------
Command:
sudo systemctl status suspicious.service --no-pager

STEP 6: Review service-related syslog messages
-----------------------------------------------
Command:
sudo grep -i suspicious /var/log/syslog

STEP 7: Review the demonstration service journal
-------------------------------------------------
Command:
sudo journalctl -u suspicious.service --no-pager

Note:
These steps create the demonstration service from the room. They do not
change the answer to the room's pre-existing-service questions below.

TASK 6: FOOTPRINTS ON DISK
==========================

Objective:
Create a Debian package in the lab and investigate dpkg.log.

ACTIVITY 1: CREATE THE SUSPICIOUS DEBIAN PACKAGE
------------------------------------------------

STEP 1: Become root
-------------------
Command:
sudo su

STEP 2: Create the package directory
------------------------------------
Command:
mkdir -p /root/malicious-package/DEBIAN

Explanation:
mkdir -p -> Creates the parent and child directories if they do not exist.

STEP 3: Create the control file
-------------------------------
Command:
cat > /root/malicious-package/DEBIAN/control <<'CONTROLFILE'
Package: malicious-package
Version: 1.0
Section: base
Priority: optional
Architecture: all
Maintainer: attacker@test.com
Description: This is a malicious Package
CONTROLFILE

STEP 4: Verify the control file
--------------------------------
Command:
cat /root/malicious-package/DEBIAN/control

STEP 5: Create the post-installation script
-------------------------------------------
Command:
cat > /root/malicious-package/DEBIAN/postinst <<'POSTINSTALL'
#!/bin/bash

# Malicious post-installation script
# It will run this script after installation

echo "something suspicious"
POSTINSTALL

STEP 6: Make postinst executable
--------------------------------
Command:
chmod 755 /root/malicious-package/DEBIAN/postinst

Explanation:
chmod -> Changes file permissions.
755   -> Owner can read/write/execute; group and others can read/execute.

Important:
Create postinst before running chmod. If the file does not exist, chmod
will return: No such file or directory.

STEP 7: Verify package contents
--------------------------------
Command:
ls -l /root/malicious-package/DEBIAN/

Expected files:
control
postinst

STEP 8: Build the Debian package
--------------------------------
Commands:
cd /root
dpkg-deb --build malicious-package

Actual output observed in this lab:
dpkg-deb: building package 'malicious-package' in 'malicious-package.deb'.

STEP 9: Install the package
---------------------------
Command:
dpkg -i /root/malicious-package.deb

Expected output includes a package setup line for malicious-package.

STEP 10: Verify installation
----------------------------
Command:
dpkg -l | grep malicious-package

The installed package status should begin with ii.

TASK 7: LINUX LOGS
==================

Objective:
Examine SSH authentication activity in the historical auth.log files.

STEP 1: Move to /var/log
------------------------
Command:
cd /var/log

STEP 2: List authentication log files
-------------------------------------
Command:
ls -lh auth.log*

Actual files observed in this lab:
auth.log
auth.log.1
auth.log.2.gz

Explanation:
auth.log      -> Current authentication log.
auth.log.1    -> Rotated, uncompressed authentication log.
auth.log.2.gz -> Older, compressed authentication log.

STEP 3: Search SSH entries for 11 September
-------------------------------------------
Command:
grep -i sshd /var/log/auth.log.1 | grep 'Sep 11'

Relevant actual log entry from this lab:
Sep 11 22:05:04 tryhackme sshd[53409]: Invalid user saqib from 10.11.75.247 port 58647

STEP 4: Search specifically for invalid SSH usernames
-----------------------------------------------------
Command:
grep -E 'Sep 11.*Invalid user' /var/log/auth.log.1

Evidence:
Invalid user saqib from 10.11.75.247 port 58647

Interpretation:
Username    -> saqib
Source IP   -> 10.11.75.247
Source port -> 58647

QUICK COMMAND REFERENCE
=======================

cd                         -> Change working directory.
ls -la                     -> List directory entries, including hidden ones.
find                       -> Search for filesystem entries.
ps aux                     -> Display running processes.
lsof -p PID                -> List open files for a process.
lsof -i -P -n              -> Display numeric network connections.
osqueryi                   -> Open the osquery interactive shell.
process_open_sockets       -> osquery table containing process socket data.
systemctl cat SERVICE      -> Display a systemd service unit.
journalctl -u SERVICE      -> Display a service's journal entries.
dpkg-deb --build DIR       -> Build a Debian package.
dpkg -i PACKAGE.deb        -> Install a Debian package.
/var/log/dpkg.log          -> Debian package manager activity log.
/var/log/auth.log          -> Authentication activity log.
grep                       -> Search text in files.
zgrep                      -> Search text in gzip-compressed files.
